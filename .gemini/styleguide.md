# GSlider Blocks - Gemini Code Review Style Guide

## Project
`gslider-blocks` is an advanced WordPress Gutenberg slider and carousel plugin (powered by Swiper) running on 2,000+ live sites. Breaking saved content or styles on existing live sites is the worst possible defect.
- Blocks live in `src/blocks/`: `base`, `flexi-content`, `flexi-content-item`, `image-slider`, `logo-carousel`, `testimonial`.
- PHP backend lives in `includes/` (`Admin`, `Assets`, `Classes`, `RestApi`, `Traits`, `Utils`, `Plugin.php`).
- The MCP server lives in `packages/mcp-server/`.

## Review rules (how to review)
1. **Concrete Evidence Only**: Report a finding ONLY if you can point to a specific changed file and line in the diff and give a concrete reason it is wrong (what breaks, for whom, and how).
2. **Zero Speculation**: No speculative findings ("might", "consider", "could potentially") without a concrete failure scenario. If unsure, ask a question instead of asserting a bug.
3. **No Style Nitpicks**: No style-only nitpicks (formatting, import order, naming, tabs or spaces, quotes). ESLint, Prettier, and Stylelint already cover them (`npm run lint:js`, `npm run lint:css`).
4. **Diff Scope**: Don't flag code the PR did not change, unless the change makes it newly broken.
5. **No Blind Approvals (Diff-Only Awareness)**: You only see the diff. You CANNOT see CI results, tests, or files outside the diff. Never say the PR is "approved", "ready to merge", or "LGTM". At most say: "No blocking issues found in the diff; merge readiness depends on CI checks and maintainer review."
6. **Severity Levels**:
   - `CRITICAL`: Data loss, broken saved blocks, or security vulnerabilities.
   - `HIGH`: Broken features, missing deprecations, or missing MCP bundle rebuilds.
   - `MEDIUM`: Real bugs in edge cases, accessibility defects, or i18n violations.
   - Do NOT report `LOW`.

## Saved data and deprecations (CRITICAL)
- Any change to a block's `save.js` output or to `attributes.js` (renamed or removed attribute, changed default, changed type or markup) MUST come with a NEW deprecation entry in that block's `deprecated.js`.
- Add the deprecation entry at the top of the array (e.g., `v1_2_0_icons`). Never edit or overwrite an existing deprecation entry such as `v1_2_0`.
- Changed defaults must not alter how already-saved blocks render.
- Flag any migration that drops user content (slides, images, text, links).

## MCP bundle sync (HIGH)
- `attributes.js`, `save.js`, `deprecated.js`, and `styling.js` are bundled into `packages/mcp-server`. If the diff changes any of them, it MUST also include the regenerated bundles under `packages/mcp-server/dist`, produced by `npm run build && npm run mcp:build`, and should mention running `npm run mcp:test`. Flag the PR if they are missing.
- SCSS, `edit.js`/inspector, `view.js`, and PHP-only changes do NOT need an MCP rebuild. Do not flag those.

## Protected core (HIGH)
- `src/components/` is protected core owned strictly by `@noruzzamans`, and all inspector panels depend on it. Flag ANY change there as high risk requiring maintainer approval.
- `src/components/` is intentionally excluded from linting; do NOT flag that exclusion.

## Generated and built files
- `includes/RestApi/defaults/*.php` is generated by `scripts/generate-block-defaults.js` (`npm run defaults:generate`, run via `npm run build`). Flag hand edits that don't match a source change.
- Admin dashboard source changes require `npm run admin:build`, with the built `assets/admin/` files committed. Files under `assets/` are filtered out of the diff you receive, so you cannot see whether they were committed: do NOT flag missing `assets/admin/` builds. At most add a one-line reminder to run `npm run admin:build`.

## Styling and lifecycle
- Dynamic CSS must go through `styling.js` and `StyleGenerator.php`. Never inline dynamic CSS in `save.js`.
- Swiper instances must be destroyed on unmount (`swiper.destroy(true, true)`).
- No `!important` rules that leak into nested sliders or global elements. Respect RTL layout and `prefers-reduced-motion`.

## Security (CRITICAL)
- PHP: Always sanitize inputs (`sanitize_text_field`, `sanitize_key`, `absint`), escape outputs (`esc_html`, `esc_attr`, `esc_url`, `wp_kses`). REST routes require a valid `permission_callback` and capability/nonce verification.
- Sanitize user-controlled CSS values, URLs (block `javascript:` and dangerous URI schemes), and SVG markup before output. Never paste exploit payloads into comments; describe the class of issue.

## i18n and accessibility (MEDIUM)
- User-facing strings must use `__()`, `_x()`, or `esc_html__()` with text domain `'gslider-blocks'` (in JS: `@wordpress/i18n`).
- Interactive elements need full keyboard access, visible focus rings, valid ARIA labels, and sufficient color contrast.

## Out of scope (ignore)
- Ignore files in `storybook/`, `docs/`, `vendor/`, `node_modules/`, `build/`, `languages/`, lock files (`package-lock.json`, `composer.lock`), and zip archives.

## Output format
1. **Summary**: 2–3 concise bullets summarizing what the PR does.
2. **Findings list**: Format each issue as:
   `[SEVERITY] path:line - Explanation of the issue, concrete impact, and suggested fix.`
   (Include a GitHub `suggestion` block when the fix is small and precise).
3. **If clean**: State "No blocking issues found in the diff; merge readiness depends on CI checks and maintainer review."
